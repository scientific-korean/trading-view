# 주봉 신호 모니터

관심 자산 28종의 주봉 지표를 매주 자동 계산해 텔레그램으로 보내고,
자체 완결형 HTML 대시보드를 만든다. **참고용이며 매매 규칙이 아니다.**

> **개인 사이드 프로젝트, 공개 저장소.** 투자 조언이 아니고, 신호의 정확도를
> 보장하지 않는다(아래 "백테스트가 답하는 질문" 참고 — 애초에 수익률을
> 검증하는 물건이 아니다). 여기 있는 어떤 것도 매매 판단의 근거로 그대로
> 쓰지 말 것. 텔레그램 토큰·chat id·ECOS API 키 등 실제 값은 이 저장소
> 어디에도 없다(`.env`는 `.gitignore` 처리돼 있음) — 이름만 나온다. `docs/`
> 아래 대시보드와 `state.json`은 매주 갱신되며 공개로 노출된다(GitHub
> Pages 사용 시).

## 신호 사양

| 항목 | 값 |
|---|---|
| 방향 | 매수 / 매도 / **중립** / 관망 (아래 참조) |
| 히스테리시스 | RSI 52 상향 → 강세 / 48 하향 → 약세 / 중간은 직전 유지 (2026-09 조정, 기존 55/45) |
| BB width | 최근 260주(5년) 분포 중 상위 5%(95백분위) 진입 시 ⚠ 표시. 자산별 상대 판정 (2026-09 변경, 기존 절대 0.8). **매매에 개입하지 않음** |
| 하드스톱 | 없음 |

**세기(강/중/약)는 폐기했다.** 실데이터 워크포워드 검증 결과 단조성
충족률이 14%로, 무작위 기대값(3그룹 순서이므로 1/6 ≈ 16.7%)보다도
낮았다. 인샘플로는 24%가 나왔던 걸 감안하면 순수 과최적화였다.
`osc_slope`(PPO/MACD 기울기) 원시값은 참고 정보로 화면에 남아 있지만
등급을 매기지는 않는다.

세기가 사라지면서 캘리브레이션 단계도 함께 사라졌다. 방향은
fast/slow/signal/RSI 임계값 같은 고정 파라미터로만 정해지는 순수
규칙 기반이라 데이터로 학습하는 값이 없고, 따라서 학습/평가 구간을
나눌 필요도 없다. `scripts/calibrate.py`, `core/walkforward.py`는
제거했다.

### 방향 4상태

| 상태 | 조건 | 의미 |
|---|---|---|
| 매수 | PPO 강세 **AND** RSI 강세 | 두 지표 일치 |
| 매도 | PPO 약세 **AND** RSI 약세 | 두 지표 일치 |
| 중립 | 두 지표 엇갈림 | **판정 보류.** 직전 확정 방향을 괄호로 병기 |
| 관망 | 워밍업 중 | 존이 아직 정해지지 않음 |

중립을 별도 상태로 둔 이유: 지표가 엇갈리는데 직전 방향을 그대로 표시하면
시스템이 확인하지 못한 것을 확인한 척하게 된다. 이건 참고용 대시보드이고
유지해야 할 포지션이 없으므로 정보 정확성이 우선이다.

합성 데이터 기준 중립 비중은 약 23%, 평균 5~6주 지속된다.

`confirmed` 필드에 마지막 확정 방향이 보존되므로 정보 손실은 없다.
**전환(◆) 은 확정 방향이 바뀔 때만 표시한다.** 중립 진출입은 `·` 로 구분 표기.

`kind: rate`(국채금리)는 PPO 대신 MACD 원값을 쓴다.
금리는 0 근처·마이너스를 오가므로 PPO 분모가 폭발한다.
표기도 매수/매도가 아닌 **상승/하락**으로 바뀐다.

**로컬 실행(2026-09~)**: `.env.example`을 `.env`로 복사해 값을 채워 넣으면
`run_weekly.py`가 시작할 때 자동으로 읽는다(`python-dotenv`). `.env`는
`.gitignore` 처리돼 있어 git에 올라가지 않는다. 이미 OS 환경변수로 설정돼
있다면 그쪽이 우선한다(`.env`가 기존 값을 덮어쓰지 않음).

**GitHub Actions 사용 시**는 `.env`가 아니라 저장소 Settings → Secrets and
variables → Actions에 위 세 개를 각각 등록해야 한다 — 로컬 `.env`와는 완전히
별개라 두 방식을 동시에 쓰면 둘 다 설정해야 한다.

**공개 저장소 주의**: `.env` 파일 자체를 절대 `git add`로 올리지 말 것
(`.gitignore`가 막아주지만, `git add -f`로 강제 추가하면 무시된다). 세
값 중 하나라도 실수로 커밋됐다면 README 수정보다 먼저 처리할 것 — 해당
서비스(BotFather/한국은행 ECOS)에서 즉시 재발급받고, git 히스토리에서
제거한다(단순 삭제 커밋만으로는 과거 커밋에 값이 남아있으므로 부족하다).

`docs/index.html`은 GitHub Pages로 공개하면 폰에서 바로 열린다(Settings →
Pages → Branch `main` / `docs` 폴더). Public 저장소이므로 이 대시보드와
`state.json`(현재 방향·RSI·OSC 등 신호 상태)은 링크를 아는 누구나 볼 수
있다 — 민감하게 여겨지면 Pages 대신 로컬에서 `docs/index.html`을 직접
열어보는 방식으로 바꿀 것.

## 신호를 고치려면

`core/signals.py`의 `generate_signal` **한 곳만** 고친다.
백테스트와 라이브가 이 함수를 똑같이 호출하므로
백테스트한 것과 실제 실행되는 것이 구조적으로 일치한다.

지켜야 할 규약:
- 순수 함수 — 파일·네트워크·전역변수·현재시각 접근 금지
- `state`는 JSON 직렬화 가능한 값만 (numpy 타입은 `float()` 변환)
- `state`를 in-place로 고치지 말고 `dict(state)`로 복사

## 백테스트가 답하는 질문

수익률 곡선이 아니다. 비중 결정이 재량이므로 수익률은 임의 가정에 좌우된다.
대신 신호 자체의 성질을 측정한다.

- **방향 정확도** — 매수 후 상승 / 매도 후 하락 비율. 기준 50%.
  종목별로 나오고, 맨 아래 종합 섹션에서 전 종목 관측치를 풀링해
  기간별(1·4·13주)·방향별로 다시 낸다. z 값이 함께 나오는데
  ±2 이상이면 대략 95% 수준에서 무작위와 구분된다는 뜻이다.
  다만 후행수익률은 주간 관측치끼리 겹쳐 자기상관이 있고 종목
  간에도 상관이 있어(대형 테크주 등) 엄밀한 유의성 검정은 아니고
  방향을 보는 참고치로 쓸 것.
- **신호 빈도·지속** — 연간 확정전환 횟수
- **중립 구간** — 비중·지속·후행 수익률
- **참고 이진곡선 2종** — strict(중립=0%) vs hold(중립=직전 유지)
- **BB width 분포** — 경고 임계치 결정용 백분위표
- **매도 지연** — 매도 확정 시점의 52주 고점 대비 낙폭

## 데이터 품질 점검 (2026-09 추가)

`core/data.py`의 `load()`가 매 호출마다(캐시 사용 여부와 무관하게) 두 가지를
점검하고 이상하면 콘솔에 `[경고]`를 찍는다. 매매를 막지는 않는다 — 눈에 띄게
알려주는 역할만 한다.

- `check_gaps`: 거래일 기준 15일 넘는 결측 구간
- `check_freshness`: 가장 최근 데이터가 오늘로부터 10일 넘게 오래됨

계기: 2026-09 ^KS200 캐시에서 7월 중순 이후 데이터가 통째로 비고 마지막 한
행은 OHL만 있고 close가 NaN인 상태로 몇 주간 아무 경고 없이 대시보드에
흘러들어간 적이 있다(`fetch_yahoo`가 `dropna(how="all")`만 써서 close 단독
NaN 행을 걸러내지 못했음 — 지금은 `dropna(subset=["close"])`로 수정).

같은 사례를 추적하다가 `load()`가 매번 `data.start`(2005년)부터 21년치를
통째로 재요청하고 있었다는 것도 확인했다. 짧은 구간(최근 1개월 등)으로
같은 티커를 요청하면 안정적으로 최신 데이터가 오는데, 21년치를 한 번에
요청하면 야후 쪽에서 간헐적으로 최근 몇 주가 빠진 채 응답이 왔다(결정적인
재현은 아니고 시점에 따라 다름 — 재현 스크립트 `check_symbol2.py` 참고).
그래서 `load()`를 **증분 갱신** 방식으로 바꿨다 — 캐시가 있으면 마지막
날짜보다 14일 전부터만 다시 받아 이어붙인다(`ecos`/`mof_jp`는 API 자체가
부분 구간을 지원하지 않아 예외, 항상 전체 재수신). 매주 21년치를 다 다시
받을 필요도 없어지는 부수효과도 있다.

**그런데도 재현되는 걸 더 보니, 구간 크기 문제가 아니라 순수 간헐적
문제였다** — 방금 성공했던 것과 완전히 같은 짧은 구간 요청을 다시 보내도
가끔 최근 데이터가 빠진 채로 온다. 그래서 `fetch_yahoo`에 **재시도**를
추가했다: 결과가 오늘로부터 5일 이내로 최신이 아니면 2초 쉬고 최대 3번까지
다시 시도하고, 그래도 안 되면 그때까지 받은 것 중 가장 최신인 걸 반환한다
(에러로 죽이지 않음). 재시도 로직 자체는 합성 데이터로 단위 테스트 완료.

## 알려진 제약

- **표본 부족**: 주봉 20년도 1,000봉 남짓. 방향 정확도는 학습되는 값이
  없어 과최적화 위험은 낮지만, 표본이 적은 종목·구간의 결과는 참고만 할 것.
- **BB width 경고 = 자산별 상대 백분위(2026-09 변경)**: 종목마다 BB width의
  타고난 스케일이 크게 달라서(예: 브렌트유 0.47 vs 원/달러 0.15) 절대 임계치
  하나로는 형평이 안 맞았다 — 옛 절대 임계치 0.8은 대부분 종목에서 사실상
  발동하지 않았다. 지금은 `core/indicators.py`의 `bb_width_percentile`이
  자산 자신의 최근 `bb_width_window_weeks`(기본 260주=5년) 분포 안에서 현재
  값이 몇 백분위인지 계산하고, `bb_width_warn_percentile`(기본 95) 이상이면
  경고한다. 윈도우가 안 찼으면(캐시 시작 후 5년 이내) 경고 판정을 보류한다.
  대시보드 BB width 패널도 고정 경고선 대신 실제 경고가 뜬 주(週)를 점으로
  표시하도록 바뀌었다. 백분위 자체를 몇으로 할지는 `scripts/backtest.py`의
  기존 백분위표로 가늠 가능.
- **osc_slope 원시값**: 세기 등급은 없지만 화면과 백테스트 결과에 raw 값은
  남아 있다. 재량 판단의 참고 자료로만 쓸 것.
- **시장 간 주봉 시점차**: 한국 금요일 종가는 미국보다 약 14시간 앞선다.
  개별 추세 판단에는 영향 없으나 시장 간 비교 시 유의.
- **선물 롤 갭**: 금·구리·브렌트유는 만기 교체 시 가격 단차가 생겨
  기울기에 가짜 스파이크를 만들 수 있다.
- **코스피 지수 티커를 ^KS200→^KS11로 교체함(2026-09)**: ^KS200(코스피200)이
  2026년 7~9월 구간에서 계속 결측/지연을 일으켜(재수신해도 간헐적으로
  실패, 아래 "데이터 품질 점검"의 재시도 로직을 넣게 된 계기) ^KS11(코스피
  종합지수)로 교체했다. 코스피200과 완전히 같은 지수는 아니지만(구성종목
  200개 vs 전종목) 상관이 매우 높아 추세 판단 목적으로는 실질적 차이가
  거의 없다. 옛 캐시(`cache/^KS200.parquet`)는 더 이상 쓰지 않으니 지워도
  된다.
- **개별주 상관**: NVDA·MSFT·GOOGL·AMZN·META·AVGO·TSM은 사실상 하나의 거래다.
  7개가 일제히 매수를 띄워도 7개의 확인이 아니라 하나의 신호다.
- **2008~2009년 결측(정상, 매주 재발함)**: `check_gaps` 경고에 아래 세 줄이
  매번 뜨는데 전부 17년 전 데이터라 현재 신호(19~39주 EMA)엔 영향 없다.
  재수신해도 안 채워짐 — 그 시절 야후 아카이브 자체의 한계로 추정.
  - USDKRW=X / JPYKRW_SYN: 2008-08-26 직전 26일 결측 (JPYKRW_SYN은
    USDKRW=X를 나눠 만드는 합성값이라 같은 결측이 그대로 옮겨감)
  - BZ=F(브렌트유): 2009-05-01 직전 17일 결측
- **GitHub Actions**: 스케줄이 수십 분 지연될 수 있고, 저장소가 60일간
  활동 없으면 자동 비활성화된다 (state 커밋이 이를 방지).
